### B2. `TBD-classification-vocabularies` — cartridges, action types, and suggestion picklists

Supersedes/amends: spec Assumptions ("caliber is a structured field… user-entered"), FR-001 (adds cartridge and optional action type), FR-012 (grouping by caliber; adds action type), data-model `caliber TEXT` (plus new cartridge column, `ActionType` and type→action tables), spreadsheet `caliber` column (plus `cartridge`, `action_type`), `FirearmSummary`, FTS index.

- [feature] caliber is somewhat ambiguous, e.g. 9x18 and 9x19 are both "9mm" but are different cartridges, .223 and 5.56x45 are also nominally the same caliber but are different cartridges, .22 Short, .22 Long, and .22 Long Rifle (LR) are all .22 caliber but are different cartridges. Need to provide a way to enter the specific cartridge and derive the caliber based on the input.
- [feature] caliber/cartridge input is just a free form field, and users may end up with multiple different ways of specifying the same information. The input should be a combo box that lets users select from existing values or input new values. the available selections should shrink based on what the user types in, e.g. if they start typing ".3" then the list might show ".30-30" and ".30 Carbine". The database should get pre-populated with the most common calibers/cartridges.
- [feature] need to be able to specify the action or sub-type of a firearm, e.g. semi-automatic, break action, revolver, lever action, pump action, bolt action, etc.
- [feature] when typing in makes, models, calibers, sub/action types, a picklist of vales should appear below the input field (e.g. as with a combo box) to suggest values already entered previously. The suggestions should narrow as the user types. The suggestions should only be based on values presently in the database, including from disposed of firearms. Deleted firearms should not leave behind any values usable by this feature.
  - **Why grouped:** the second caliber item and the picklist item are the same combobox mechanism, and the cartridge catalog, action type, and make/model suggestions all share it. They also all add or reshape lookup data.
  - **RESOLVED 2026-09-19 (decision #4): seed the *suggestions*, not the database.** The "pre-populated" wording in the caliber item is read as: the app ships a built-in catalog of common cartridges that feeds the combobox, in addition to values derived from the user's own firearm records. Nothing is written to the user's database, so a built-in cartridge that no firearm uses is not residue and the "deleted firearms leave nothing behind" rule (constitution V) holds by construction. Purpose of the catalog: quality of life (common cartridges are selectable instead of typed) and *formatting hints* showing how the user might name their own cartridges.
  - **Design consequences to carry into `/speckit-specify` for this spec:**
    - **Suggestion sources are merged at query time:** (1) `SELECT DISTINCT` of the field over all firearm rows, active and disposed (existing item's rule); (2) the bundled read-only catalog, shipped as an app resource like the generic thumbnails (research §10), not a DB table or migration. Deduplicate case-insensitively so "9x19mm" appears once if both sources have it. A value the user typed but never saved on a firearm is never remembered; delete the last firearm using a custom cartridge and it disappears from suggestions.
    - **The firearm record must be self-contained.** Since the catalog is not in the DB, the record stores its own cartridge string *and* its derived caliber (so grouping by caliber, FR-012, works without the catalog). Selecting a catalog entry copies its cartridge name and caliber onto the record. Catalog changes in later app versions never alter existing records.
    - **RESOLVED (caliber for a custom cartridge): guess, pre-populate, user may override.** A catalog cartridge maps to its caliber exactly. For a cartridge not in the catalog the app derives a best-effort guess and pre-fills the caliber field. The guess is visible and editable before saving, and once the user has edited the caliber field, later cartridge edits must not overwrite it. Caliber stays required (FR-001), so grouping never has a gap; if a name doesn't parse, leave the field empty and ask rather than guess wrong. On import, if `caliber` is blank but a cartridge is given, derive it (catalog first, then the guess) and list those rows in the import report so a guess is never silent. The heuristic needs a test corpus of real names (.22 LR, .300 BLK, 7.62x39, 9x19, .45 ACP, 12 gauge...).
    - **RESOLVED (normalization): yes, visibly, for make, model, cartridge, and caliber.** (Action type is a closed list, below.) Rules to carry into the spec:
      - *Equivalence* ignores case, spacing and separator variants: "9mm" = "9 mm", "9x19" = "9 x 19" = "9×19", "Smith & Wesson" = "Smith and Wesson" = "Smith&Wesson" (`&` ≡ `and` is a token rule). The field snaps on entry so the user sees it before saving; on import it snaps and the report counts the changes. A built-in spelling wins over a user's variant; otherwise the most-used existing spelling wins.
      - *Guide, never restrict.* (Revised after review.) The catalog and suggestions steer users toward specific cartridges, but free entry is always accepted within reason: non-empty, trimmed, a sensible length cap, no control characters. Nothing requires a value to exist in the catalog. Many users mean 9x19 when they say "9mm" and may not know other 9mm cartridges exist, and recording "9mm" is acceptable. So a bare "9mm" is kept as typed (not blocked, not snapped); the list narrows to the specific 9mm cartridges, most common first (9x19mm Parabellum, then .380 ACP, 9x18 Makarov, 9x21...), and the user may pick one or decline. A suggestion is never applied unless the user chooses it. The same principle applies to make, model and caliber. Action type is the one closed list.
      - *Snapping is for same-notation variants only.* Case, spacing, separator and `&`/`and` variants of the same text snap to each other: "9 mm" → "9mm", "9 x 19" → "9x19", "Smith and Wesson" → "Smith & Wesson", when the target is on record or is a catalog spelling. Different notations are **not** snapped ("9mm", "9x19" and "9x19mm Parabellum" stay as entered). Catalog aliases ("9mm Luger", "9mm Para", "9x19") only narrow and rank the suggestion list. (This drops my earlier unique-alias snapping, which conflicted with "record it however you want".) Consequences: catalog entries need a commonness rank to order suggestions, and the caliber guess for "9mm" is simply "9mm".
      - *Abbreviations and acronyms narrow the suggestion list only; they never auto-snap.* Narrowing modes: prefix, word-prefix ("smith w"), and initialism ignoring `&` and spaces ("sw" or "s&w" finds Smith & Wesson; "hk" finds Heckler & Koch), run against the merged suggestion pool; catalog aliases add ".22 LR" ↔ ".22 Long Rifle" and similar. Abbreviations that aren't initialisms (e.g. "CZ" for Česká zbrojovka) match only if the value is on record under that spelling. No built-in make-alias list is planned; makes and models stay derived-only.
      - Only new entries and imports are normalized. Existing records that already differ ("S&W" vs "Smith & Wesson") stay split. A later "merge/rename value" cleanup tool is a possible follow-up, not part of B2 unless wanted.
    - **RESOLVED (action type): a closed choice from a fixed, pre-populated list, not a combobox and not part of the suggestion mechanism.** Modeled like `FirearmType`: a seeded `ActionType` lookup table (migration), nullable FK on Firearm, and new values arrive only with app updates ("generalize, or ask for an update"). Choices are **filtered by firearm type** through a seeded type→action mapping (join table, since e.g. semi-automatic applies to several types). To define in the spec:
      - Seed list content and the mapping. Your starting set: semi-automatic, break action, revolver, lever action, pump action, bolt action. Likely additions: single-shot, falling/rolling block, muzzleloader ignition types. Decide how to treat full-auto/select-fire.
      - Fallback: `FirearmType` is user-extensible, and a user-added type or "Other" has no mapping, so show the whole list.
      - Changing the firearm type after choosing an action that the new type doesn't allow: clear the action with a notice.
      - The field is optional; existing records get none and group as "Unspecified".
      - Import/export: `action_type` matched case-insensitively against the list; unknown or not-allowed-for-type is a row error (same as `firearm_type`); export writes the name.
      - It is a structured field, so it becomes groupable (FR-012) and searchable via a join like the type name.
      - This removes action type from the picklist item above; that item keeps make, model, cartridge, caliber.
    - **Migration: not applicable (decided 2026-09-20).** The app is unreleased (`0.1.0`, no tags), so there is no obligation to migrate or preserve data from earlier development builds. Nothing in the constitution or the 001 specs requires it. Schema changes for B2 need no data-mapping or backfill design. Developers with existing databases either add an ordinary new migration or recreate their DB. If a compatibility policy is wanted in writing, a one-line pre-1.0 clause in the constitution would settle it for good.
    - **UI:** show catalog entries and the user's own entries in one narrowing list, but visually distinguish the source (e.g. a "built-in" marker or grouping) so the catalog can act as the formatting hint. Matching should be forgiving of leading dots and separators ("30" or ".30" finds ".30-30" and ".30 Carbine") and use the abbreviation/initialism modes above.
    - **Precedent, not a conflict:** `FirearmType` *is* seeded into the DB (migration 0003) because it is a real lookup table with an FK from `firearms`. Cartridge is deliberately different: no FK, free-text on the record.

### B6. `TBD-revert-restore-import` — general change history / undo / import

- [feature] while editing an existing record (firearm or insurance), a visual indication that a change has been made needs to be provided next to each input, along with a way to revert that specific change to the saved value. If the form has no remaining changes, its save button should be disabled. The save button should only be enabled when the form has changes vs what is saved in all cases.
- [feature] users should be able to revert changes to a record by retrieving its old data from a backup. The app should provide a button to restore individual records from the backup databases, including fields, photos, and documents. The user should be shown the differences and they can choose what to restore. If a firearm record was scheduled on an insurance policy that only exists in the backup and if that insurance policy in the backup is still active according to the dates, the user should be asked what to do. They can either restore the firearm and ignore the insurance policy, or they can also restore that insurance policy. The restore from backup also needs to apply to insurance policies. Basically the entire constitutional or existing requirements issue about delete really means delete is sidestepped because it is pulling the information from a backup database. The restore functionality needs to be able to open multiple backups in case what the user wants isn't in the most recent backup. This feature might share some implementation with the next feature about import from other hoplodex databases.
- [feature] users should be able to import (copy, or move) records from other hoplodex databases, not just spreadsheets. This may not be a very common use case, but it exists nonetheless. If not for the previous feature about restoring from backups then this feature might not be worth implementing by itself, but it doesn't sound like a big stretch to have both features if either one was implemented.

### B8. (as-yet-undefined) NFA and other regulated item types — suppressors and similar

Supersedes/amends: FR-001, FR-012, FirearmType (seeded Handgun/Rifle/Shotgun/Other, extensible), the generic thumbnails (FR-009), spec Assumptions on firearm types, and B2's type→action mapping.

- [feature, added 2026-09-21] Expand the types to cover items such as suppressors and other NFA items. Whether each currently NFA-registered category **continues to require registration is in flux because of current events**, so this is a Track B spec, not a plain type addition.
  - **Why separate:** it changes what the record *is*, not just a label. Several things assumed in 001 don't hold for these items, and the legal status is volatile.
  - **Design consequence to settle first: keep regulatory status out of the code.** Model item *type* (what it is) separately from any registration/legal status (what the rules currently say), and make the status a data-driven attribute the user can edit or that updates with the app, rather than a hard-coded "this type is NFA". Otherwise a law change means a schema and code change. Decide how much the app should assert about legality at all: recording what the *owner* says (e.g. "registered", "tax stamp date") is a much smaller commitment than the app deciding what is regulated. The scope should say so plainly, as feature 002 did for the regulatory-history scope.
  - **Candidate types (needs research, not a decision):** suppressors, short-barreled rifles and shotguns, any-other-weapons, machine guns, destructive devices. Each is a `FirearmType` (or a new classification) with its own thumbnail (FR-009 needs art per type, plus the generic fallback).
  - **001 assumptions that break for these items:**
    - *Caliber (FR-001, required):* a suppressor is rated for a range of calibers, not chambered in one; a destructive device has a bore diameter. May need "caliber rating" semantics, or an exemption from FR-001's required caliber for some types.
    - *Serial number (FR-029/030/032):* suppressors are serialized, so the uniqueness rule applies, but registered-item rules and marking requirements differ by type and era (overlaps feature 002, `specs/002-firearm-identification/`).
    - *"Firearm" wording:* the app, the spec and the UI call every record a "firearm". Some of these items aren't one in ordinary usage, so decide on neutral wording ("item" or "record") and whether it is worth changing.
    - *Type→action mapping (B2):* action type doesn't apply to a suppressor; the mapping needs a "no action type" case.
  - **Candidate registration data (not decided):** approval/tax-stamp date, form number, trust or entity name, and the approval document. The document itself is already covered by the existing attachments (FR-010); the question is which fields deserve structure. These are sensitive, so any new field is subject to constitution V (what leaves the device, including the spreadsheet export, which is unencrypted).
  - **Dependencies:** the barrel/overall length fields (FR-039) (a length below a legal threshold is what makes an SBR or SBS) is the input to any future "this configuration may be regulated" hint, if wanted; B2's type→action mapping; feature 002's identity and marking rules. Insurance (FR-014, FR-036) should be checked for whether such items are scheduled differently.
  - **Open questions for `/speckit-specify`:** how far the app goes in asserting legal status (record only vs. hint vs. warn); what happens to existing records when a type's status changes; whether users can define their own classification like `FirearmType` already lets them add types; whether any of this warrants a warning or disclosure at first use.

Emit one generated file that the frontend imports, or that the Rust side exposes through a command, and hook the generation into `npm run build` so it can't go stale. Also ship it as a plain-text file in the bundles.

### C10. Windows development and test environment

- [infrastructure] Added 2026-09-26: a Windows environment for building, testing and developing the Windows-specific code (`platform/windows.rs`, and the `cfg(windows)` branches in `secure_delete`, `file_swap`, `disk_space`, `backups` and `session/fingerprint`). Its E2E and screenshot runs are Windows' share of A5's "other platforms" item. Nothing is built yet.
  - **Rejected: a Windows dev container.** Podman on Windows runs Linux containers only, so it would need Docker in Windows-container mode and a PowerShell wrapper. Windows containers have no desktop, so E2E, screenshots, `tauri dev` and human testing can't run in one (WebView2 isn't supported on Server Core). A container never sleeps, locks or logs off, so the most Windows-specific code can't be triggered either. What's left (build, `cargo test`, lint, audits) didn't justify an image of 15–25 GB.
  - **Blocker for any Windows E2E run: the harness isn't isolated on Windows.** `e2e/wdio.conf.ts` sets `APPDATA`/`LOCALAPPDATA`, but Tauri resolves its directories through `dirs`, which on Windows calls `SHGetKnownFolderPath` and ignores those variables (checked in `dirs-sys` 0.5). An E2E run on a real Windows machine would write the real `%APPDATA%\com.hoplodex.app\machine.json`. Harmless on a throwaway VM or runner, but it has to be fixed before E2E on Windows counts, most likely with a config-directory override honored only by E2E builds. The rest of the harness is Linux-only too: the seed step (`XDG_CONFIG_HOME`), the `xdg-open` stub (Windows needs its own, or opening a document launches a real viewer), stale-port cleanup (`ss`), the native-driver lookup (Windows needs an `msedgedriver` matching the WebView2 version; not needed if C12 replaces `tauri-driver`), `scripts/human-testing.sh` (bash) and `e2e/scripts/quit-cleanup.py` (Unix signals). Whole-page screenshots rely on a 1920×4200 Xvfb screen. Windows normally won't size a window taller than the screen, so long captures need another technique.
  - **GitHub-hosted Windows runner (for C2).** These runners have a logged-in desktop, Edge, WebView2 and a matching `msedgedriver` (`EDGEWEBDRIVER`), and no GPU (WebView2 renders in software).
    - *Can run:* build, `cargo test`, Vitest, lint, clippy, fmt, the audits, and very likely E2E and screenshots once the harness is ported. The runner is disposable, so the isolation gap doesn't matter there and a real Credential Manager keyring test would be safe.
    - *Can't run:* sleep/resume (the runner can't be suspended), shutdown/log-off (it ends the job), screen lock (nothing can unlock it again) or human testing.
    - *Caveats:* the desktop reportedly defaults to 1024×768, smaller than the 1200×800 screenshot window, so a job step has to raise it. Windows minutes cost more than Linux ones on private repos. Check GitHub's current table for runner specs.
    - *Covering the event handlers anyway:* a test can find the hidden window and send it synthetic `WM_POWERBROADCAST`/`PBT_APMSUSPEND`, `WM_WTSSESSION_CHANGE`/`WTS_SESSION_LOCK` and `WM_QUERYENDSESSION` messages. That tests the handlers on any Windows, runners included, but not that the OS delivers the events.
  - **Chosen direction: a VM, provisioned without depending on the hypervisor.** It will run on Proxmox.
    - *Hypervisor-agnostic layer:* `autounattend.xml` for an unattended install with a local account, an idempotent `provision.ps1`, and a Linux script (`xorriso`) that packs them onto a seed ISO. On any hypervisor: attach the Windows ISO and the seed ISO, boot, and wait.
    - *Proxmox layer:* a thin `qm create` script. Packer only if repeatable golden images are wanted later; a snapshot after provisioning is enough for one VM.
    - *Proposed location:* `scripts/windows-vm/`, plus a "Windows VM" section in `DEVELOPMENT.md`.
    - *`provision.ps1` installs:* Visual Studio Build Tools (C++ workload and Windows SDK), Git, rustup (stable, rustfmt, clippy), Node 24 with npm 12, vcpkg with `openssl:x64-windows-static-md` and `OPENSSL_DIR`/`OPENSSL_STATIC` (OpenSSL 3.x, per C3), `tauri-driver` and an `msedgedriver` matching WebView2 (both dropped if C12 lands), `cargo-deny`, OpenSSH server, and the qemu guest agent. It also sets 100% display scaling, a Defender exclusion for the build directories, auto-logon for the test user, and active hours with no automatic restarts while signed in.
  - **Driving the VM from the Linux host.** Commands over SSH run in a session with no desktop. That's fine for `cargo test`, but E2E and screenshots can't open a window there. A disconnected RDP session stops rendering, so screenshots come out black. So: auto-logon keeps a desktop session, a helper runs commands in it (a scheduled task that runs only while the user is logged on) and returns the log, and people watch through the Proxmox console or SPICE, not RDP. Clone the repo on the VM's own disk: a network share is slow and changes SQLite locking and the file-identity check.
  - **What only the VM covers:**
    - *Screen lock:* Win+L in the console. Easy.
    - *Shutdown:* a clean shutdown through the guest agent or ACPI, reverted with a snapshot. Easy.
    - *Sleep:* hibernate through the guest agent (`qm guest cmd <id> suspend-disk`), which also raises `PBT_APMSUSPEND`. Reasonable. S3 suspend under QEMU/OVMF is unreliable.
  - **VM specs:**
    - *vCPU:* 4 minimum, 8 recommended, CPU type `host`. E2E builds release, which compiles SQLCipher and the Tauri stack.
    - *RAM:* 8 GB minimum, 16 GB recommended, ballooning off.
    - *Disk:* 80 GB minimum, 128 GB thin-provisioned recommended, VirtIO SCSI single with iothread, discard and SSD emulation. Windows is about 30 GB, Build Tools about 10 GB, and debug plus release `target` directories 20–30 GB.
    - *Proxmox settings:* `q35`, OVMF with an EFI disk and a TPM 2.0 state disk (Windows 11 requires TPM), VirtIO network, and the virtio-win drivers ISO during install (`autounattend.xml` loads its storage and network drivers).
    - *GPU:* not needed. WebView2 falls back to software rendering, and the default VGA or VirtIO-GPU display is enough.
  - **Edition: Windows 11 Enterprise evaluation (90 days, rebuilt from the scripts).** Home is what most users run, and the app doesn't depend on edition. WebView2, Credential Manager and the power/session messages are the same, and the disk-encryption note (FR-008) is a fixed message, not a BitLocker check. But Home has no free evaluation, so the scripts stay edition-neutral: picking the edition is one line in `autounattend.xml`. Home also lacks an RDP host and Group Policy (provisioning uses the registry anyway), and pushes hard for a Microsoft account at setup. The unattend local account is the step most likely to break on a new Windows build.
  - **Release note (for C2): no Microsoft or Apple store distribution.** Laptops often ship with Windows 11 Home in S mode, which runs Store apps only. Those users have to leave S mode to install HoploDex; the install docs should say so.
  - **Open:** whether provisioning also installs `gh` and Claude Code; and whether the E2E harness port and the synthetic-message tests come before or after the VM scripts. The VM scripts can't be tested from a Linux session, so expect fixes after the first install.

### C11. macOS development and test environment

- [infrastructure] Added 2026-09-26: a macOS environment for building, testing and developing the macOS-specific code (`platform/macos.rs`: IOKit sleep/wake, the `com.apple.screenIsLocked` notice and NSWorkspace's power-off notice; the `target_os = "macos"` branches in `secure_delete` and `machine_settings`). Its E2E and screenshot runs are macOS's share of A5's "other platforms" item. Nothing is built yet. The request was "a macOS container for build/dev/test", with Tart suggested.
  - **There is no macOS container.** A container shares the host's kernel, and no runtime runs a macOS userland that way: Docker and Podman on a Mac run Linux containers inside a Linux VM, and so does Apple's own `container` tool. (The experimental Darwin chroot-style projects need SIP turned off and have no desktop.) So the choice is which macOS VM, and the objections that sank the Windows container don't carry over: a macOS VM has a full desktop, so `tauri dev`, screenshots and human testing can run in it.
  - **Tart is a VM manager with a container-style workflow**, not a container. Images are pulled from and pushed to OCI registries (Cirrus Labs publishes `ghcr.io/cirruslabs/macos-*`), then `tart clone`/`tart run`, SSH or `tart exec`, `--dir` for shared folders. It's built on Apple's Virtualization.framework, so:
    - *It needs an Apple Silicon Mac running macOS as the host.* It can't run on the Linux workstation or on Proxmox. This is the deciding limitation: whichever option is chosen, a Mac has to be bought, rented or borrowed.
    - *Licensing:* Apple's macOS licence allows up to two extra macOS copies in VMs, only on Apple hardware, and Virtualization.framework enforces two running at once. Tart is Fair Source 100: royalty-free on personal workstations, paid past 100 CPU cores of server installations per organization.
    - *Clone the repo onto the VM's disk*, not a `--dir` share, for the same SQLite-locking and file-identity reasons as the Windows VM.
    - *Not verified:* whether a macOS guest can really sleep (does `pmset sleepnow` in the guest raise IOKit's sleep notice?). Pausing or suspending the VM from the host does not; the guest doesn't see it. Screen lock (Ctrl+Cmd+Q in the VM window) and a clean shutdown (a snapshot, i.e. a `tart clone`, reverts it) should work.
  - **Rejected: macOS on Proxmox or QEMU (OSX-KVM, Docker-OSX).** It violates Apple's licence (macOS only on Apple hardware), breaks across updates, and is Intel-only. macOS 26 Tahoe is the last release for Intel Macs, so it has no future.
  - **Blocker for any macOS E2E run, on any Mac: there is no WebDriver for WKWebView.** `tauri-driver` supports only Linux (WebKitWebDriver) and Windows (msedgedriver). Every macOS option puts a driver inside the app. The proposed fix is C12: switch every platform to one embedded driver, rather than use a macOS-only driver.
  - **Harness isolation on macOS: an environment variable fixes it, unlike Windows.** Tauri's directories come from `dirs`, which on macOS builds `~/Library/Application Support` from `$HOME` (checked in `dirs-sys` 0.5). `wdio.conf.ts` sets only the `XDG_*` variables, which macOS ignores, so today an E2E run on a Mac would write the real `~/Library/Application Support/com.hoplodex.app/machine.json`. Pointing `HOME` at the sandbox should fix it. `mock-keyring` already keeps E2E out of the Keychain. The rest of the harness is Linux-only: the seed step (`XDG_CONFIG_HOME`); the `xdg-open` stub (the opener plugin calls `open` on macOS, possibly by absolute path, which a stub on `PATH` wouldn't catch); stale-port cleanup (`ss`; macOS has `lsof`); and whole-page screenshots, which rely on a 1920×4200 Xvfb screen. macOS also keeps windows within the screen, so either give the VM a tall display (`tart set --display`, not verified at that size) or capture another way. `scripts/human-testing.sh` and `e2e/scripts/quit-cleanup.py` probably port easily, since macOS has bash and Unix signals, but they're untested there.
  - **Options, in the order suggested:**
    - *A used or refurbished Apple Silicon Mac mini (M1 or later, 16 GB RAM, 512 GB disk).* It's the only option that covers everything. Run the app on the Mac itself for real sleep, wake, lock and shutdown, and use Tart VMs on it for clean, disposable builds, E2E and screenshots (a `tart clone` of a provisioned image instead of a Proxmox snapshot). Drive it from the Linux host over SSH, and watch through macOS Screen Sharing, which a Linux VNC client can connect to.
    - *GitHub-hosted macOS runner (for C2).* Apple Silicon VMs with a logged-in desktop. *Can run:* build, `cargo test`, Vitest, lint, clippy, fmt, the audits, and E2E and screenshots once the WKWebView driver and the harness port above exist. *Can't run:* sleep, shutdown, screen lock or human testing (the same limits as the Windows runner). macOS minutes cost several times Linux minutes on private repos; check GitHub's current table.
    - *A rented cloud Mac* (e.g. AWS EC2 Mac, which bills a 24-hour minimum per Apple's licence, or monthly providers such as MacStadium or Scaleway). It works like owning one, including Tart, but after a few months it costs more than a used Mac mini.
    - *Covering the event handlers without real sleep:* any process can post the `com.apple.screenIsLocked`/`com.apple.screenIsUnlocked` distributed notifications, so a test can exercise the lock handler on any Mac, runners included. IOKit's sleep notice and NSWorkspace's power-off notice can't be faked from outside the app. They need either a test hook that calls the handler directly, or real hardware.
  - **If Tart is used, provisioning mirrors C10's hypervisor-agnostic idea:** an idempotent `provision.sh` run over SSH on a Cirrus base image (not the Xcode image: Tauri needs only the Command Line Tools). It installs Homebrew, rustup (stable, rustfmt, clippy), Node 24 with npm 12, `cargo-deny` and the chosen WKWebView driver. It also turns off sleep and the screen saver for E2E runs, and keeps auto-login (Cirrus images have it on). The Mac's `tart` commands then go in a thin wrapper. Proposed location: `scripts/macos-vm/`, plus a "macOS VM" section in `DEVELOPMENT.md`. SQLCipher uses CommonCrypto on macOS rather than OpenSSL, so check that the `bundled-sqlcipher` build and the license notes (C3, C9) hold there.
  - **Release note (for C2):** outside the App Store, a macOS build downloaded from the web has to be signed with a Developer ID and notarized, or Gatekeeper blocks it. That needs the Apple Developer Program (paid, yearly). Local builds from source run without it.
  - **Open:** buy, rent or CI-only; whether a macOS guest can sleep.

### C12. One E2E driver on every platform

- [infrastructure] Added 2026-09-27: run the E2E suite the same way on Linux, Windows and macOS, so a test passes or fails because of the app, not the platform's driver. Tests that need an OS event (sleep, lock, shutdown) stay platform-specific (C10, C11); no WebDriver can trigger those.
  - **Today:** `e2e/wdio.conf.ts` starts `tauri-driver`, a thin relay from the Tauri team to each webview's own driver: WebKitWebDriver on Linux, msedgedriver on Windows, nothing on macOS. Those drivers send real input through the engine (key presses count as genuine, and a click fails if something covers the element).
  - **Proposed: WebdriverIO's embedded driver, `tauri-plugin-wdio-webdriver`** (1.4.0, MIT, from the WebdriverIO project), on all three platforms, Linux included, dropping `tauri-driver`. It's a W3C WebDriver server compiled into the app, on `127.0.0.1` (port from `TAURI_WEBDRIVER_PORT`, default 4445). Checked in its 1.4.0 source:
    - *Input is JavaScript in the page, the same code on every platform.* A click is `el.click()` (a click event only: no pointer or mouse-down events, and no check that something covers the element). Typing sets the value through the native setter and fires one `input` and one `change` event. Key presses are `KeyboardEvent`s the browser marks untrusted, and the driver copies a few default behaviours by hand (arrow keys on radio buttons, Ctrl+A); the rest don't happen.
    - *Screenshots are native on each platform:* WebKitGTK's snapshot (visible area), WebView2's `CapturePreview` and WKWebView's `takeSnapshot`. Window size goes through Tauri's `set_size`.
    - *Deleting a session doesn't close the app;* the server only forgets the session.
  - **Why it costs little fidelity here:** `e2e/support/ui.ts` already clicks and fills fields through page JavaScript (`element.click()`, the native value setter plus `input`/`change`), because WebKitWebDriver's own click and `setValue` were unreliable. So the suite already works the way the embedded driver does. The main exception is Escape (`pressEscape()` and `browser.keys(["Escape"])` in us1, us3, us4, us6). It should still pass: Radix listens for Escape on the whole document and doesn't check whether the key press was genuine. Where untrusted keys do break: a native `<dialog>` on WebView2 ignores a synthetic Escape (webdriverio/desktop-mobile #612). The app uses Radix dialogs, not `<dialog>`; keep it that way or test such a dialog another way.
  - **What `tauri-driver` still has:** no test code in the app, and a small relay over the engines' own drivers, where the embedded driver reimplements WebDriver and part of the browser's behaviour in about 10,000 lines. **What it costs:** no macOS; two different engines' drivers with their own quirks, which is why `wdio.conf.ts` has the `findNativeDriver` search and stale-port cleanup, and why Windows needs an msedgedriver matching WebView2.
  - **Rejected: `tauri-driver` on Linux and Windows plus an embedded driver on macOS.** A key press would be genuine on two platforms and synthetic on the third, the opposite of the goal. Other embedded drivers (Choochmeque's `tauri-plugin-webdriver`, `danielraffel/tauri-webdriver`) work the same way. As far as known, CrabNebula's macOS mode also needs a plugin in the app, plus a paid key.
  - **Security: the embedded server must never reach a shipped build.** It has no authentication and runs any JavaScript inside the app, so any local process could read an unlocked collection through it. Put it behind a Cargo feature that only E2E builds enable, tied to `mock-keyring` (a build with the mock keyring can't ship anyway), and add a check that a release build doesn't contain it. This is a persistence/security-relevant change for the constitution's PR gates, and the release security review (C8) should cover the gate.
  - **Plan: try it on Linux first**, in the dev container, where the suite passes today:
    - Add the plugin behind the E2E feature. Have the harness launch the app with `TAURI_WEBDRIVER_PORT` set and point the wdio config at it, instead of starting `tauri-driver`. The isolation variables are inherited as before.
    - Relaunching the app: `browser.reloadSession()` (us4, us7) relies on a new session starting a new app process. Either use `@wdio/tauri-service`, which launches the app itself, or add a harness helper that kills and restarts it.
    - The service's companion plugin `tauri-plugin-wdio` (mocking, `withGlobalTauri`) isn't wanted: the tests never mock. Check that the service works without it, or skip the service and keep the current config.
    - Run all specs and the screenshot walk; compare the screenshots with a `tauri-driver` run.
    - The new crates (axum and others) go through the dependency audit and the license check (C3).
    - If it passes, remove `tauri-driver`, its setup in `DEVELOPMENT.md` and the dev container, and update the comment at the top of `e2e/support/ui.ts`. Windows (C10) and macOS (C11) then need only their platform-specific harness parts, not a driver.
