# Tasks: Cartridges, Action Types & Entry Suggestions

**Input**: Design documents from `/specs/004-cartridges-action-types/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/ (tauri-commands.md, spreadsheet-format.md, ui-entry.md), quickstart.md (all present)

**Tests**: The project constitution's Testing Standards principle is NON-NEGOTIABLE: every user story below includes test tasks written first (integration tests run the real `ops` against a temporary SQLCipher database, no mocks), expected to fail, then implementation makes them pass.

**Organization**: Tasks are grouped by user story (spec.md's priorities P1–P4) so each story can be implemented and tested on its own. This feature is a **delta** against `specs/001-firearms-inventory/` and `specs/002-firearm-identification/`: most tasks edit existing files (plan.md's Project Structure), and the schema is edited in place in migrations 0001–0003 (CLAUDE.md).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependency on an incomplete task)
- **[Story]**: Which user story this task belongs to (US1–US4)
- Exact file paths are given per plan.md's Project Structure
- Work that must be built, tested or run on a specific platform gets one task per platform

## Path Conventions

Existing Tauri desktop app: Rust backend in `src-tauri/`, React/TypeScript frontend in `src/`, WebdriverIO E2E suite in `e2e/`. No new project, package, dependency or layer (plan.md's Structure Decision). Run tests, lint and screenshots through `scripts/dev-container.sh` (CLAUDE.md; commands in quickstart.md).

## How the stories divide the shared pieces

- **US1** owns the cartridge column, the catalog, caliber derivation (`derive_caliber`), the entry rules on save, `settle_entry` returning the derived caliber (value trimmed, `changedBy: null`), the caliber state on the form (with plain text fields), cartridge grouping and display, and the "Unspecified" rename.
- **US2** adds ranking (`suggest_entries`), snapping inside `settle_entry` (`changedBy`, and the derived caliber snapped), the shared `Combobox` and `EntryField`, which replace US1's plain fields.
- **US3** is independent of US1/US2 apart from the Foundational schema.
- **US4** extends export/import and reuses US1's derivation, US2's snapping and US3's action rule.

## Implementation Strategy

### MVP First (User Story 1 Only)

1. Phase 1 Setup and Phase 2 Foundational.
2. Phase 3: User Story 1.

### Incremental Delivery

1. Foundational → schema, model and entry key.
2. US1 → cartridges with derived calibers (MVP).
3. US2 → the suggestion list and snapping on the four fields.
4. US3 → action types.
5. US4 → export and import catch up with every new field and rule.
6. Polish → performance, screenshots, amendment pointers, CLAUDE.md, the full gates and the manual checks.

Each story adds value without breaking the previous ones; stop at any checkpoint to validate.
