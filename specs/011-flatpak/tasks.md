# Tasks: Build and Distribute a Flatpak

**Input**: Design documents from `/specs/011-flatpak/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/ (tauri-commands.md, flatpak-bundle.md), quickstart.md (all present)

**Tests**: The project constitution's Testing Standards principle is NON-NEGOTIABLE: every user story below includes test tasks written first, expected to fail, then made to pass by the implementation, each at the level plan.md's Test Levels gives it. Reach and the refusals are tested in Rust on real files and real databases (`--features test-kdf`); the portal opener against a stand-in portal on a private bus; the build's checks in Vitest against red fixtures; the journeys in the one new E2E file, `e2e/specs/flatpak.e2e.ts`, which runs the real Flatpak in its sandbox in the dev container through `npm run test:flatpak` and is left out of `npm run test:e2e`. No test reads real data, a real keyring or the developer's Flatpak installation (SC-007).

**Organization**: Tasks are grouped by user story (spec.md's P1–P3). **The phases run in dependency order, not priority order**: the two P1 stories' E2E journeys run the built Flatpak (US3, P2) through the automated check (US5, P3), so Phase 3 is US3 (the build), Phase 4 is US5 (the check's harness), then US1, US2 and US4. US1's and US2's Rust and Vitest work needs only Phase 2 and can start alongside Phase 3; only their E2E journeys wait for Phases 3 and 4. No database, layout, `machine.json` field, keyring entry, command or capability is added (contracts/tauri-commands.md, "Unchanged"), so `commands_list.rs`, `capabilities/default.json`, the migrations and `examples/human_seed.rs`'s data stay as they are.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependency on an incomplete task)
- **[Story]**: Which user story this task belongs to (US1–US5)
- Exact file paths are given per plan.md's Project Structure
- In this file, bare IDs (FR-001, US1, T012) mean this feature's. In code, comments and test names, cite them with the feature's number: `011 FR-004`, `011 US1-8`, `011 T012`, `011 research.md §5` (DEVELOPMENT.md, "Spec citations"); `npm test` fails on a bare one
- Work that must be built, tested or run on a specific platform gets one task per platform, starting with the platform's name

## Path Conventions

Existing Tauri desktop app: Rust backend in `src-tauri/`, React/TypeScript frontend in `src/`, WebdriverIO E2E suite in `e2e/`. The Flatpak's own files go in a new top-level `flatpak/`, its scripts in `scripts/flatpak/`. Run tests, lint, the audit and the build through `scripts/dev-container.sh` (CLAUDE.md); every Flatpak command needs its new `--flatpak` option (T003). The first Flatpak build in a container fetches about 2 GB from Flathub: run it in the background with its output in a log (CLAUDE.md, "Waiting on a background run"). Script tests under `scripts/flatpak/` start with `// @vitest-environment node`, as `scripts/licenses/`'s do (the suite's default is jsdom). Every new Rust test file is a module of the one `integration` program and needs a `mod` line in `src-tauri/tests/integration.rs` (`test_files_test` fails without it); a test file written before its API exists breaks every other `cargo test`, so write those in a worktree and merge once the API compiles (CLAUDE.md memory "Worktree test writers"). Never open the real databases, `machine.json`, backups or keyring entries, and never run `flatpak` against the developer's own installation (CLAUDE.md, "Never touch the real databases").

- **Foundational** owns `services/sandbox.rs` (`Reach`, `Grant`, `Need`, `HostPaths`, the `/.flatpak-info` parser, `Reach::check`), `CommandError::out_of_reach`, `Reach` as Tauri state, the dev container's Flatpak tooling and `--flatpak` option, and the scripts' host guard (`guard.mjs`, `env.sh`), since every later Flatpak command runs behind it.

- **US5** owns the automated check's harness: `checkManifest.mjs` and its rule, `check.sh`, `e2e/support/flatpak.ts`, `launchApp`'s launcher, `wdio.conf.ts`'s Flatpak mode, the bus checks, `flatpak.e2e.ts`'s skeleton, the isolation proof (SC-007) and DEVELOPMENT.md's check section with the FR-021 path list.

- **US2** owns `session/auto`, WebKit's sandbox inside Flatpak (the probe and 007's amendment), the US2 journey and the research record for the release review (research.md §9, §20).
- **US4** owns `flathub.json`, the linter and its exceptions, the `.flatpak` file, `--fresh-install` and the install-over step.

## Implementation Strategy

### MVP First

The smallest useful increment is a Flatpak a Linux user can keep their collection in: Phase 1, Phase 2, US3 (the build), US5's harness (Phase 4) and US1.

1. Complete Setup and Foundational.
2. Start US1's backend and frontend (T038–T040, T042–T052) alongside US3.
3. Finish US3: the Flatpak builds offline and installs.
4. Finish US5's harness, then US1's journey (T041, T053).
5. **STOP and VALIDATE**: the US1 journey passes in the sandbox; every refusal test passes.

### Incremental Delivery

1. Setup + Foundational → reach and the guard exist.
2. US3 → the Flatpak builds; the build checks fail on their red fixtures.
3. US5 → the check runs the real Flatpak away from real data.
4. US1 → collectors' journey in the sandbox (MVP).
5. US2 → the protections hold; the record for #21.
6. US4 → the release file, the linter, fresh install and upgrade.
7. Polish and close-out → other platforms unchanged, manual steps, the PR.
