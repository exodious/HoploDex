# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

HoploDex is a local-only firearm collection inventory app: Tauri 2 with a Rust backend (`src-tauri/`) that owns persistence, encryption and business logic, and a React 18 + TypeScript frontend (`src/`) that owns the UI.

## Commands

`DEVELOPMENT.md` is the single source for development instructions: the dev container, prerequisites, and the build, test (including single-file and single-spec runs), lint, dependency and license audit, screenshot and human-testing commands. Read the relevant section before running any of them. One thing that catches people out: run `npm run build` before `test:e2e` or `screenshots`, since the E2E build embeds whatever is in `dist/`.

## Run tests in the dev container

On a host with podman, run tests, lint, the dependency audit and screenshots through `scripts/dev-container.sh` by default, not directly on the host: put the command after the wrapper, and use `bash -c '...'` to chain several.
- **Already inside?** Check first. The container's working directory is `/workspace` and its hostname is `hoplodex-dev`. If both match, run the commands directly and don't nest the wrapper.
- **First runs are slow** (image build, then an empty `node_modules` and `target`). Give long commands a generous timeout, or run them in the background.
- **Waiting on a background run:** redirect its output to a log file, end it with a short summary (`echo "exit $?"` plus a `grep` for passing/failing), and wait for the completion notification. Don't write `until …; sleep` poll loops. Don't end a background command with `| tail -N` either: nothing reaches the output file until the command exits, so it looks hung.
- Don't use the options that pass the host's identity through (`--git-config`, `--ssh-agent`, `--gh-token`, `--anthropic-api-key`) unless the user asks. Commit from the host. `--gui` is only for `tauri dev` and human testing; tests don't need it.
- Use `--build` after a `Dockerfile` change. Never use `--reset-volumes=all` without asking, because it logs the user out of `gh` and `claude`.
- Run tests directly on the host only if podman isn't available or the user asks.
- **A UI bug a spec can't reproduce** (a focus ring, a layout that fixes itself on the next key press or mouse move) may need real input, which WebDriver's clicks and keys aren't. See "Real keyboard and mouse input" in `DEVELOPMENT.md`.

## Never touch the real databases

The developer uses the app day to day, and their real data is more than one file: every `.hoplodex` database they have created or opened, wherever it lives (the suggested place is `<Documents>/HoploDex`), its backups (in `HoploDex backups` next to it, or a folder they chose), `machine.json` with the recent-databases list in the app's config directory (`~/.config/io.github.exodious.HoploDex/`), and each saved passphrase, a `passphrase:<database id>` entry under `io.github.exodious.HoploDex` in the OS keyring. Never open, modify or delete any of it from a session. Tests, E2E runs, screenshots and human testing are all isolated from it; "Test isolation" in `DEVELOPMENT.md` says how. Keep it that way when you change any of them: take every path (database, config directory) as a parameter, keep keyring user names under the `passphrase:` prefix, and don't run the app outside that tooling.

## Commit and push

Commit and push automatically whenever you finish implementing something the user directed, without waiting for them to separately say "commit and push". Commit every change git doesn't ignore: modified, deleted and untracked files, including changes made before the session started or outside it, not only your own. Review `git status` and `git diff` first. Stop and ask if something looks like it shouldn't be committed, such as secrets, credentials, large binaries or stray scratch files.

Never push to `main`. If the current branch is `main`, create a new branch first (name it for the work) before committing and pushing.

## Architecture

**IPC boundary.** The frontend reaches the backend only through `invoke()` in `src/services/tauriClient.ts`. It turns a backend rejection into a typed `CommandFailure { code, message, fieldErrors }`, which mirrors `CommandError` in `src-tauri/src/commands/error.rs`. That is the only error shape a command returns. Codes are stable strings (`VALIDATION_ERROR`, `NOT_FOUND`, `INTERNAL_ERROR`, domain codes such as `ORIGINAL_MARKS_MATCH`, and the session's `DATABASE_CLOSED`, `DATABASE_TAKEN_OVER`, `PENDING_CHANGES_UNRESOLVED` and friends, and for 007's preview `PREVIEW_UNSUPPORTED`, `PDF_PREVIEW_UNAVAILABLE`, `PREVIEW_DAMAGED`, `PREVIEW_FAILED`, `PREVIEW_PAGE_FAILED`, `PREVIEW_CLOSED` and `NO_APP_FOR_DOCUMENT`). Raw DB errors are logged and never forwarded (`CommandError::from_db`). Some warnings can be overridden: the command fails with a warning code, and the UI resends it with `confirmedWarnings: true`.

**Backend layering** (`src-tauri/src/`):
- `commands/<area>.rs` holds each area's `#[tauri::command]` functions. They are thin: they go through the `Session` state, then call the matching function in that file's `pub mod ops`. Collection commands use `session.read(...)` or `session.write(...)`, which refuse with `DATABASE_CLOSED` when nothing is open and `PENDING_CHANGES_UNRESOLVED` while a lock's pending changes wait. `write` also checks the file's fingerprint first, so another computer's take-over closes the session without writing. Session housekeeping uses `write_housekeeping`/`inspect`. `ops` functions take `&Connection` and hold the actual logic. Integration tests and `examples/human_seed.rs` call `ops` directly, so they exercise the same code paths as the app. `commands/databases.rs` (chooser, create, open, close, lock, settings, saved passphrase) and `commands/backups.rs` (list, restore, passphrase change) are feature 003's.
- `session/` owns the open database (feature 003): `Session` holds at most one `OpenDatabase`, a single `Connection` behind a `Mutex` with no pool, deliberately. It holds the file's exclusive lock and SQLCipher's derived key, never the passphrase. `lifecycle.rs` opens, closes (normal close with its automatic backup, lock, immediate close on sleep/shutdown) and reacts to OS events; `operations.rs` tracks the one long-running operation; `idle.rs` is the idle lock; `pending.rs` stages the open form's unsaved input and writes it as pending changes on a lock; `fingerprint.rs` detects take-over.
- `models/` holds the serde types (camelCase over IPC), input validation (`validate_*_input`) and enums. `models/record.rs` has `RecordRef` (firearm or accessory by id) and `RecordLabel`, the one shape for "a record" in a mount, a list or a link; photos, documents and disposition history take an `owner: RecordRef` rather than a firearm id. `models/rules.rs` holds the amount, date, disposition and insurance rules a firearm and an accessory share, so the two can't judge them differently.
- `services/` holds pure/domain logic: spreadsheet import/export (`FIREARM_COLUMNS` and `ACCESSORY_COLUMNS` are the canonical column lists, one per table; import recognises each sheet's table by its header and reads columns by header, so a sheet exported before a column existed still imports, and one file or two can carry both tables; import passes a row's `record_id` to `create_firearm` and `create_accessory`, whose `uid` argument is `None` everywhere else, so the identifier and `mounted_on` survive), import matching, insurance status, valuation, attachment storage, secure delete, and for 003 `passphrase` (NFC-normalized, zeroized), `machine_settings` (`machine.json`), `keyring` (saved passphrases), `backups`, `file_swap` (atomic file replacement; `recover` runs before every open) and `disk_space`; and for 004 `entry_text` (the entry key and FR-015 rules), `cartridges` (the embedded catalog and caliber derivation) and `suggestions` (ranking, snapping, the import sheet pass); for 005 `registration` (the built-in form names, used only as suggestions); and for 006 `mounts` (`MountGraph`, a scan of the `mounts` table that every mount rule goes through: no cycles, one host per record, the descendants of a record; `atomically` runs a multi-write change in one savepoint) and `record_id` (the random UUID that names a record across export and import); and for 007 `document_types` (the one allowlist: `classify` checks a file's content at attach, preview and open), `consent` (`Consent`, `needs_consent`, the native confirmation's text before a document goes to another app) and `preview/` (the next bullet). `commands/entries.rs` holds `suggest_entries`, `settle_entry`, `list_action_types`, `list_firearm_types` and `list_registration_classes`. For 006, `commands/accessories.rs` holds the accessory commands (an accessory is its own table, `accessories`, with the same create, update, dispose, reverse and delete shape as a firearm's), and `commands/mounts.rs` holds `mount_record`, `list_mount_candidates` and `ops::dispose_with_mounted`, which both `dispose_*` ops call to dispose of a record and the mounted records chosen with it in one step.
- `services/preview/` (feature 007) shows a document without writing it to disk. `Preview` lives in `OpenDatabase`, so closing or locking the database closes the preview. The `hdpreview` protocol (`protocol_handler.rs`) serves one document's bytes by token to the web views, which have no file access. A PDF is shown by the OS web view's own viewer in a child web view over the page area (`surface/`, one file per OS plus `frame_script.js`; no network, no IPC reach, no toolbar actions). `availability.rs` holds `PdfAvailability` and the hold (`pdfPreviewHold` in `machine.json`: set on macOS when the watch catches a copy of a document, it keeps PDF preview off until the app is updated). A TIFF is decoded in a confined child, `hoplodex --render-helper` (`helper.rs`, `confine.rs`), and text in `text.rs`. On Linux `sandbox_probe.rs` runs the app once with `--webkit-sandbox-probe` and turns WebKit's sandbox on only where it works. `commands/preview.rs` holds `open_preview`, `set_preview_bounds`, `focus_preview`, `render_preview_page` and `close_preview`. Read `specs/007-document-preview/research.md` before changing any of it.
- `db/mod.rs` creates and opens passphrase-keyed databases (`create_database`, `open_database`), always from a path the caller passes, and applies `db/migrations/*.sql`, tracked in `schema_migrations`, which is also the data-layout version: a migration this build doesn't know means `NewerVersion`. Each connection gets `db/cipher.rs`'s pinned `CIPHER_SETTINGS`, then foreign keys, `secure_delete` and `locking_mode = EXCLUSIVE`. `db::reclaim_deleted_record` merges both search indexes after any delete (a delete cascades through a mount, so either record's words may be in either). Never change a cipher setting: every existing file becomes unreadable (`tests/portability_test.rs`). Read an open database's bytes only through `db/raw_file.rs` (SQLite's own file handle), never `std::fs`: closing any other descriptor on the file drops the process's POSIX lock on it.
- `app_dirs.rs` is where the startup and every command get the app's config and cache directories and the documents and home folders. Don't call `app.path()` for them directly: an E2E build takes them from the sandbox's `HOPLODEX_E2E_*` variables instead of the OS, and won't start without them, because Windows' known folders ignore `APPDATA` and the like. It also names the web views' data folders (the main window's and the PDF surface's, under the cache directory), so `WEBVIEW2_USER_DATA_FOLDER` is never set.
- `platform/` turns the OS's sleep, wake, screen-lock and shutdown notices into `SystemEvent`s for `session::lifecycle`.
- `main.rs` registers plugins and state, and lists every command in `generate_handler!`. A new command must also go in `commands_list.rs`'s `COMMANDS` (which `build.rs` turns into the app's ACL manifest) and `capabilities/default.json` as `allow-<command>`, for the main web view only; `tests/acl_manifest_test.rs` fails when the three differ. It handles `--render-helper` and `--webkit-sandbox-probe` before anything else, and builds the main window in `setup()` (so it has its own web view data folder) rather than from `tauri.conf.json`. No database is open at startup: it manages `Session` and `MachineSettings` (with the system keyring), sweeps unfinished backups, and starts the system-event listener and the idle clock's 1 s tick. Closing the window or quitting emits `app:quit-requested` so the frontend can ask about unsaved changes; an OS shutdown or SIGTERM/SIGHUP/SIGINT closes at once, keeping unsaved input as pending changes. It clears decrypted document copies on exit, on those signals and at startup (FR-035).

**Frontend** (`src/`): `features/<area>/` each has a `*Service.ts` (typed wrappers over `invoke`, one per command), `types.ts` mirroring the Rust models, and the components and CSS. `features/app/` holds the shell, navigation, theme, and `CollectionProvider`/`collectionStore` (shared collection state: policies, value summary). `features/session/SessionProvider` shows the database chooser whenever nothing is open and renders the collection's providers only while a database is, keyed by that open, so a close or switch drops all collection state; it also handles the unsaved-changes question, pending changes after a lock, Ctrl/⌘+L and idle activity. `features/databases/` holds the chooser, create dialog, database menu and its dialogs (settings, change passphrase, restore, the guide); its `plate/` is the chooser's animated catalogue plate, whose timing lives in `plate/timing.ts` and is tuned with `npm run tuner` (`tools/plate-tuner/`, see DEVELOPMENT.md). The program icon is generated from `tools/icons/AppIcon.tsx` with `npm run icons`. The frontend reads the firearm types (and which fields each has) and the registration classes from the backend, with no hard-coded list; `IdentificationGuide` is the "How do I record this?" guide (it was `OriginGuide`). Shared primitives, built on Radix, live in `src/components/` and are exported from `index.ts` (`Menu.tsx` also has radio items, used by the collection's grouping menu); `Combobox.tsx` is the shared suggestion list. `features/accessories/` holds the Accessories page, `AccessoryForm` and `AccessoryRecordPage`; `features/mounts/` is shared by both record pages and both dispose and delete dialogs: `RecordName` (a record's name, as a link or text), `MountChooser` (the "Mounted on" combobox), `MountedList`/`MountedSection` (the flat depth-first Mounted list and its Mount menu), `MountedOnChain` and `DeleteMountedNote`. `features/media/` holds photos and documents: `DocumentList`, `DocumentPreview` (the viewer, a dialog over the record), `PreviewSurface` (the page area the backend lays the PDF's child web view over, reporting its bounds), `mediaService.ts` and, for the per-computer "Open documents" setting, `documentOpening.ts`. `features/browse/` is shared by the collection and Accessories pages: `GroupByMenu`, `searchHooks.ts` (the search debounce and the "/" shortcut) and `MountLines`. Design tokens are in `src/styles/tokens.css`. Money values are **whole dollars** (integers), not cents; see `src/lib/money.ts`.

**File drops** arrive as filesystem paths through Tauri's native drag-drop event (`listenForFileDrops`). They go to the `add_*_from_path` commands. WebKitGTK gives HTML5 drops no `File`, so leave `dragDropEnabled` at its default and don't switch to HTML5 file drops.

## Conventions that aren't obvious from the code

- **Schema changes edit the existing migrations in place** (`0001_initial.sql`, `0002_fts5.sql`, `0003_seed_firearm_types.sql`) while the app is unreleased. Don't add a data migration. Existing local databases become incompatible, so tell the user instead of touching their databases.
- **Keep the human-testing seed in step with the data model.** When you add a column, table or spreadsheet column, seed a record that uses it in `src-tauri/examples/human_seed.rs` and add it to the import samples, in the same change. `tests/human_seed_coverage_test.rs` fails otherwise. Fix it by seeding, not by loosening the test.
- **UI consistency is a constitution principle.** When you change a pattern in one form or dialog (field widths, grouping, labels, hints), carry it to the others: FirearmForm, DisposeDialog, RestoreDialog, CoverageDialog, AccessoryForm, DocumentPreview, InsurancePolicyForm, PolicyDeleteDialog, Import/ExportDialog. Consent for a decrypted copy leaving the app (opening a document in another app, or choosing that as the setting) uses `services::consent`'s native dialog, not `ConfirmDialog`, so that no web view content can answer it. Short fields use the `hd-field--quarter`/`hd-field--third` and `hd-form-grid--*` classes in `src/features/firearms/forms.css`. If a change adds a screen, add it to the walk in `e2e/screenshots/screens.e2e.ts`.
- **Tests hit real persistence and never mock the DB.** Every behavior change needs a test, and bug fixes need a regression test (constitution II).
- CI is disabled on purpose (`.github/workflows-disabled/`). Don't re-enable it or flag its absence.

## Spec Kit workflow

Features are specified under `specs/NNN-name/` (`spec.md`, `plan.md`, `data-model.md`, `contracts/tauri-commands.md`, `contracts/spreadsheet-format.md`, `tasks.md`), driven by the `/speckit-*` skills. `.specify/feature.json` names the active feature. Code comments cite requirement IDs (`FR-033`, `research.md §5`). Keep those references accurate, and update the contracts when a command's shape changes. The constitution in `.specify/memory/constitution.md` overrides other guidance. Its gates: lint, tests and the dependency audit pass, UI PRs carry before/after screenshots, persistence PRs describe how they meet the security/data-handling constraints, and performance-sensitive PRs note their impact against the budgets (search ≤500ms and actions ≤1s at 10,000 items). Before every release, a whole-codebase AI-assisted security review runs and its dated report is committed.

Planned work is tracked as GitHub issues. Issues labeled `needs spec` go through `/speckit-specify`. Copy the issue's original request (verbatim) and its recorded decisions into the new spec's `## Source Request` section, and cite the issue number there, so the spec stands on its own.

When a feature settles part of another issue (as 006 does for #53's record identifiers), updating that issue is part of closing out the feature, done when its pull request is opened, not before: comment with what was settled and what is left, and bring the issue's open questions up to date. At `/speckit-plan`, list each related issue and what to post in a "Close-out (at pull request time)" subsection of `plan.md`, so `/speckit-tasks` puts it in the final phase.
