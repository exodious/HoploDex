# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

HoploDex is a local-only firearm collection inventory app: Tauri 2 with a Rust backend (`src-tauri/`) that owns persistence, encryption and business logic, and a React 18 + TypeScript frontend (`src/`) that owns the UI.

## Commands

`DEVELOPMENT.md` is the single source for development instructions: the dev container, prerequisites, and the build, test (including single-file and single-spec runs), lint, dependency and license audit, screenshot and human-testing commands. Read the relevant section before running any of them. One thing that catches people out: run `npm run build` before `test:e2e` or `screenshots`, since the E2E build embeds whatever is in `dist/`.

## Run tests in the dev container

On a host with podman, run tests, lint, the dependency audit and screenshots through `scripts/dev-container.sh` by default, not directly on the host: put the command after the wrapper, and use `bash -c '...'` to chain several.
- **Already inside?** Check first. The container's working directory is `/workspace` and its hostname is `hoplodex-dev`. If both match, run the commands directly and don't nest the wrapper.
- **First runs are slow** (image build, then an empty `node_modules` and `target`). Give long commands a generous timeout, or run them in the background.
- **Waiting on a background run:** redirect its output to a log file, end it with a short summary (`echo "exit $?"` plus a `grep` for passing/failing), and wait for the completion notification. Don't write `until …; sleep` poll loops. Don't end a background command with `| tail -N` either: nothing reaches the output file until the command exits, so it looks hung.
- Don't use the options that pass the host's identity through (`--git-config`, `--ssh-agent`, `--gh-token`, `--anthropic-api-key`) unless the user asks. Commit from the host. `--gui` is only for `tauri dev` and human testing; tests don't need it.
- **Flatpak commands need `--flatpak`.** `npm run bundle:flatpak`, `npm run flatpak:sources` and `npm run test:flatpak` run only in `scripts/dev-container.sh --flatpak ...` (it unmasks `/proc` for that run, which `bwrap` needs); anywhere else the guard refuses, except `test:flatpak` on an opted-in GitHub-hosted runner (`DEVELOPMENT.md`, "Flatpak", "The Flatpak check").
- Use `--build` after a `Dockerfile` change. Never use `--reset-volumes=all` without asking, because it logs the user out of `gh` and `claude`.
- Run tests directly on the host only if podman isn't available or the user asks.
- **A failure seen on only one OS** is fixed only once it has been rerun on that OS (several runs in a row for a flake). Passing on another OS doesn't verify it.
- **A UI bug a spec can't reproduce** (a focus ring, a layout that fixes itself on the next key press or mouse move) may need real input, which WebDriver's clicks and keys aren't. See "Real keyboard and mouse input" in `DEVELOPMENT.md`.

## Never touch the real databases

The developer uses the app day to day, and their real data is more than one file: every `.hoplodex` database they have created or opened, wherever it lives (the suggested place is `<Documents>/HoploDex`), its backups (in `HoploDex backups` next to it, or a folder they chose), `machine.json` with the recent-databases list in the app's config directory (`~/.config/io.github.exodious.HoploDex/`), and each saved passphrase, a `passphrase:<database id>` entry under `io.github.exodious.HoploDex` in the OS keyring. Never open, modify or delete any of it from a session. Tests, E2E runs, screenshots and human testing are all isolated from it; "Test isolation" in `DEVELOPMENT.md` says how. Keep it that way when you change any of them: take every path (database, config directory) as a parameter, keep keyring user names under the `passphrase:` prefix, and don't run the app outside that tooling.

**`wdio session`** drives the app step by step, and only `npm run session` does it in the sandbox. Never `wdio session open tauri <app>` or `open <app>` (they launch the real binary on the real databases) or `open ./e2e/wdio.conf.ts` (not the way in; the launcher opens `e2e/session.conf.ts`): "Drive the app with wdio session" in `DEVELOPMENT.md`.

## Commit and push

Commit and push automatically whenever you finish implementing something the user directed, without waiting for them to separately say "commit and push". Commit every change git doesn't ignore: modified, deleted and untracked files, including changes made before the session started or outside it, not only your own. Review `git status` and `git diff` first. Stop and ask if something looks like it shouldn't be committed, such as secrets, credentials, large binaries or stray scratch files.

Never push to `main`. If the current branch is `main`, create a new branch first (name it for the work) before committing and pushing.

## Conventions that aren't obvious from the code

- **Schema changes edit the existing migrations in place until 0.1.0 is tagged** (`0001_initial.sql`, `0002_fts5.sql`, `0003_seed_firearm_types.sql`). Don't add a data migration, and tell the user that existing local databases become incompatible instead of touching their databases. Rerun `cargo run --example release_fixture` whenever the layout changes before the tag. **From the tag on, every change is a new step in `db/migrations/`**: released steps never change (`released.txt`, `tests/released_migrations_test.rs`), and each new step is covered by `tests/release_upgrade_test.rs` (009 research.md §11, §12).
- **Keep the human-testing seed in step with the data model.** When you add a column, table or spreadsheet column, seed a record that uses it in `src-tauri/examples/human_seed.rs` and add it to the import samples, in the same change. `tests/human_seed_coverage_test.rs` fails otherwise. Fix it by seeding, not by loosening the test.
- **UI consistency is a constitution principle.** When you change a pattern in one form or dialog (field widths, grouping, labels, hints), carry it to the others: FirearmForm, DisposeDialog, RestoreDialog, CoverageDialog, AccessoryForm, DocumentPreview, InsurancePolicyForm, PolicyDeleteDialog, Import/ExportDialog, AboutDialog. Consent for a decrypted copy leaving the app (opening a document in another app, or choosing that as the setting) uses `services::consent`'s native dialog, not `ConfirmDialog`, so that no web view content can answer it. Short fields use the `hd-field--quarter`/`hd-field--third` and `hd-form-grid--*` classes in `src/features/firearms/forms.css`. If a change adds a screen, add it to the walk in `e2e/screenshots/screens.e2e.ts`.
- **E2E files are named for the setup they share**, not a spec or story (`locking.e2e.ts`); each story's tests are a `describe("<spec> US<n> - <the spec's heading>")`, and a new journey joins the file whose setup it shares, whatever its spec, since every file adds start-up time (DEVELOPMENT.md, "E2E files").
- **One Enter rule (#44).** Enter in a single-line field submits the dialog's or form's primary action when it's enabled; in a textarea it adds a line; on a button it activates that button; on a radio, checkbox or select it only operates the control (`radioKeys.ts`'s `keepEnterOut` for radios); in a combobox it picks a highlighted row first; and it never acts while an input method is composing. So every dialog that takes input is a `<form>` with a `type="submit"` primary button, and `ConfirmDialog` is one too: a non-destructive question with nothing to fill in opens with focus on confirm, a destructive one on Cancel.
- **A log line carries nothing from inside a database** (`logging.rs`): no record's values, no photo's or document's original file name (nor the path it was attached from, nor a copy named after it: log `logging::folder_of`), no draft's text (`logging::json_error`, since serde_json quotes what it read), never a passphrase. The paths of databases, backups and the app's own files may be named.
- **Tests hit real persistence and never mock the DB.** Every behavior change needs a test, and bug fixes need a regression test (constitution II). Test it at the cheapest level that can show it: E2E only for a story's journey, a form's error mechanisms, what needs the real app, and security properties that depend on it (the plan template's "Test Levels").
- Full CI (format, lint, tests and the app build on every OS, #25) isn't implemented yet; don't add it unasked or flag its absence. Only the focused workflows run: CodeQL (`codeql.yml`) and the dependency audit (`audit.yml`), which passes a Markdown-only PR without running. Pin a third-party action to a commit (#72) and a GitHub-owned one (`actions/*`, `github/*`) to a release tag; Dependabot updates both.

## Spec Kit workflow

Features are specified under `specs/NNN-name/` (`spec.md`, `plan.md`, `data-model.md`, `contracts/tauri-commands.md`, `contracts/spreadsheet-format.md`, `tasks.md`), driven by the `/speckit-*` skills. `.specify/feature.json` names the active feature. Code comments and test names cite requirements with their spec's number, since every spec numbers its own (#121): `003 FR-040`, `006 SC-002`, `001 US2`, `007 US3-2` (story 3, scenario 2), `008 T050`, `007 research.md §5`; one number covers a list (`006 FR-001, FR-002`). Bare IDs are only for a spec's own folder. `scripts/citations.mjs` (run by `npm test`) fails on a bare citation in `src/`, `src-tauri/`, `e2e/`, `scripts/` or `tools/`, or one its spec doesn't have, but not on the wrong spec: check what the cited text says (DEVELOPMENT.md, "Spec citations"). Keep those references accurate, and update the contracts when a command's shape changes. The constitution in `.specify/memory/constitution.md` overrides other guidance. Its gates (a PR that changes only Markdown is exempt from all but review): lint, tests and the dependency and license audit pass (Dependabot's PRs too), CodeQL adds no error-level or high-or-above alert (the `Default` ruleset holds this), UI PRs carry before/after screenshots, persistence PRs describe how they meet the security/data-handling constraints, and performance-sensitive PRs note their impact against the budgets (search ≤500ms and actions ≤1s at 10,000 items). Before every release, the license checks the tools can't make are done by hand, and a whole-codebase AI-assisted security review runs at the release commit with its findings uploaded to code scanning; no release while a critical or high code scanning, Dependabot or secret scanning alert is open (each is fixed, or dismissed with its reason). Security findings live in GitHub's security features, not in committed documents. After a release, a vulnerability in a released version goes through a private security advisory, never a public issue or PR, until a fixed release is out (`SECURITY.md`).

A merged feature's `specs/NNN-name/` is the record of what was decided then, so don't rewrite it when a later feature or fix changes things. Leave its text, tables and examples as they are and add a one-line italic note beside what changed: `_Amended by [spec NNN](../NNN-name/<file>.md): …_` when a feature changes it, `_Amended <date>: …_` for a fix outside one, or `_Superseded by …_` when it no longer applies. Say what is true now and link to where it is recorded. Edit the old text itself only for a mechanical rename (an identifier, a path) that would otherwise leave a broken reference. What stays current is the code, this file, `DEVELOPMENT.md`, `docs/architecture.md` and the active feature's own artifacts.

Planned work is tracked as GitHub issues. Issues labeled `needs spec` go through `/speckit-specify`. Copy the issue's original request (verbatim) and its recorded decisions into the new spec's `## Source Request` section, and cite the issue number there, so the spec stands on its own.

When a feature settles part of another issue (as 006 does for #53's record identifiers), updating that issue is part of closing out the feature, done when its pull request is opened, not before: comment with what was settled and what is left, and bring the issue's open questions up to date. At `/speckit-plan`, list each related issue and what to post in a "Close-out (at pull request time)" subsection of `plan.md`, so `/speckit-tasks` puts it in the final phase. That list is a draft by the time the pull request opens: check each issue's state first (`gh issue view <n> --json state`), and don't comment on a closed issue unless the user asks, even when the plan says to. If the work regresses a closed issue's fix and the pull request won't fix it, open a new issue that links to the old one, rather than commenting on or reopening it.
